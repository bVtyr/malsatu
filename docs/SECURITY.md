# Безопасность и целостность логики

Итог статического ревью (2026-10-22): три независимых прохода (безопасность API, бизнес-логика, веб-клиент), ~65 замечаний, все устранены в коде. Код **не компилировался и не запускался** — первый запуск `pnpm install && pnpm test` обязателен.

## Аутентификация и сессии
- Сессия: непрозрачный токен, в БД хранится sha256. Выдаётся и как httpOnly-cookie `ms_session` (SameSite=Lax, Secure в prod), и в теле ответа (для PWA/мобильных).
- CSRF: мутирующие запросы с cookie-аутентификацией принимаются только с `content-type: application/json` или заголовком `x-requested-with: MalSatu` (multipart).
- OTP: код хэшируется HMAC, 6+ цифр, лимит попыток инкрементируется атомарно (`UPDATE … WHERE attempts < max`), 5 запросов/час на номер, чёрный список номеров, старые коды гасятся. Принимаются только мобильные РК `+7 7xx`.
- WebSocket чата: аутентификация по cookie либо первым кадром `{type:"auth",token}` в течение 5 с; typing-события только участникам диалога.
- Заблокированный пользователь не получает `req.user` ни по cookie, ни по Bearer.
- Prod-guard в `config.ts`: запуск падает при дефолтных секретах, mock SMS/платежах, отсутствии `CALL_WEBHOOK_SECRET`.

## Сделки (deals)
- Переходы статусов — compare-and-set по ожидаемому статусу (двойной confirm/cancel невозможен), одна выплата на сделку (уникальный индекс), один активный платёж.
- `pay` — только системное действие после ответа провайдера; покупатель не может сам «оплатить».
- Удержанная сумма: бронь = предоплата, эскроу = полная сумма; комиссия ≤ удержанного; частичный возврат строго внутри (0, held).
- Продавец не может открыть окно осмотра при доставке не самовывозом; спор требует причины ≥10 символов; отзыв — только по неденежной сделке в 30 дней, без дублей.
- Количество списывается атомарно при создании (кроме direct), восстанавливается при отмене/возврате; редактирование объявления не опускает остаток ниже открытых сделок.
- Оффер привязывается к одной сделке (уникальный индекс), количество ≤ оффера, лот per_lot продаётся целиком, объявления «Куплю» не продаются.

## Складчина (sogym pool)
- Резерв и оплата доли — в транзакции с `SELECT … FOR UPDATE`; оплата только в `open` и до дедлайна.
- Дедлайн: возвраты выполняются **до** смены статуса, платёж помечается условным UPDATE до вызова провайдера → повторный тик ничего не вернёт дважды; незавершённые возвраты добираются на следующем тике.
- Отмена организатором возвращает оплаченные доли; машина состояний `open→cancelled, filled→slaughtered|cancelled, slaughtered→distributed, distributed→completed`.
- Сбор можно привязать только к своему объявлению либо к себе как продавцу.

## Фоновые задачи
- Каждый тик берёт `pg_try_advisory_lock('job:<name>')` — при нескольких репликах API задача не дублируется.
- Тихие часы считаются в часовом поясе пользователя (`Asia/Almaty`), а не сервера; доставка откладывается, а не теряется.
- Индекс цен исключает `negotiable` и `per_lot`; рассылка по «Куплю» идемпотентна.

## Объявления, модерация, карантин
- Одобрение только из `pending_moderation`/`hidden_quarantine` и не удалённых; `published_at` ставится при одобрении; архив закрывает очередь модерации.
- Существенное изменение объявления (цена/описание/медиа) возвращает его на модерацию; медиа и документы можно привязывать только свои.
- Карантин: виды берутся из категорий в БД, при снятии зоны срок объявления продлевается, заблокированные заявки на перевозку открываются.
- Доверие (`trust_score` 0..100, CHECK) пересчитывается при завершении сделки, решении спора и отклонении объявления.

## Геоданные
- В БД триггером поддерживаются `public_lat/public_lng` (округление до 0.01°, ~1 км). Наружу при `address_hidden` уходят только они: bbox-фильтр, карта, расстояние считаются по публичной точке — границами запроса нельзя «нащупать» двор.
- Геолокация в браузере запрашивается только по кнопке, хранится округлённой 24 часа.

## Прочее
- Push-подписки: endpoint только `https` на известных шлюзах (FCM, Mozilla, WNS, APNs) — исключён SSRF через наш же веб-push.
- Медиа: `complete` проверяет объект в S3 (HeadObject, размер, mime); magic-байты проверяются при загрузке через API.
- Поиск: триграммный оператор `%` (использует GIN-индекс), префикс `:*` только для слов ≥4 букв, счётчик результатов ограничен 1000, sitemap кэшируется час; ILIKE экранируется.
- Жалобы: одна открытая жалоба на пару (заявитель, цель), авто-скрытие считает уникальных заявителей.
- Вебхук звонков защищён `x-webhook-secret` (timing-safe); вебхук платежей — заглушка, подпись реализуется под конкретного провайдера (см. INTEGRATIONS.md).
- Логи: redact `authorization`, `cookie`, `x-webhook-secret`, `token=` в URL. `trustProxy` настраивается числом хопов.
- Схемы: ключи атрибутов ≤64 символов, JSON ≤20 КБ, цена ≤1e12, количество ≤1e6, CSV-импорт ≤500 строк, рассылка ≤5000 получателей.
- Веб: CSP/заголовки безопасности в `next.config.mjs`, экранирование `</script>` в JSON-LD, `credentials: include`, logout только на 401/403, черновики офлайн привязаны к владельцу.

## Платежи, аукционы, тендеры, верификация (добавлено 2026-10-22)
- Вебхук провайдера: подпись HMAC-SHA256 по сырому телу (парсер сохраняет строку только в scope модуля), timing-safe сравнение, сверка суммы, условный UPDATE `pending→succeeded`; mock-провайдер принимает вебхук только вне production.
- Аукцион: ставка в транзакции с `FOR UPDATE`, чужие `max_auto` и идентификаторы участников наружу не отдаются, владелец не ставит на свой лот, отмена с ставками — только администратор, депозиты возвращаются идемпотентно.
- Тендер: предложения видит только покупатель (продавец — своё), ставки только при `verification_level ≥ 2`, присуждение — CAS по статусу.
- Верификация: ИИН хранится только у подтверждённого аккаунта, наружу — маска `9001******17`, уникальный индекс запрещает один ИИН на два аккаунта, модератор не подтверждает себя, документы — только своё медиа со статусом `ready`.

## Не закрыто / требует внешних действий
- Маппинг полей `createSignedProvider` под выбранного платёжного партнёра (контракт и подпись уже реализованы).
- Верификация ИИН/БИН и документов (уровни 3–4) — внешняя интеграция.
- Нагрузочное и интеграционное тестирование после первого запуска.
